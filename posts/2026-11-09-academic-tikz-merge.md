## 一句话结论

Skills 不是越多越好，真正稀缺的是注意力。要降低的是「该不该用技能、用哪个」的选择成本：简单需求交给内置能力，特定场景才上专用技能，而且同一类场景只留一个入口。

## 背景：为什么会聊到这个

Skills 数量多、花样更新快，很容易迷失。我另有一个仓库 [skill-router-v3](https://github.com/Eastr5/skill-router-v3) 也是为了治理 skills：它在上层做路由，让 AI 按意图自动选该用哪个技能、MCP 或工具。academic-tikz 则是从源头治理，把重叠的技能直接合并。

2026-10-19 我下载了三个功能高度重叠的 TikZ 绘图技能：tikz-diagrams、tikz-figure-skill、tikz-scientific-figures。同时装着，技能名会互相抢触发。10 月 29 日我把它们合并成了 [academic-tikz](https://github.com/Eastr5/academic-tikz)。

先说明：模板、脚本和 recipes 的主体都来自这三个开源上游，我做的是整合与路由设计，不是从零创作。

## 讨论中的关键点

1. **真正的成本是选择，不是能力。** 当人要去找、比较、试用一堆 skills 时，注意力会被摩擦耗尽。三个同类技能单独用都没问题，问题是用户和 agent 都要先判断该用哪个。
2. **底层驱动决定上限。** 我最初用 Python 画学术图，效果不理想，所以改成本地部署 LaTeX 编译器。LaTeX 和 Python 的绘图底层不同，不是换个技能名就能互相替代。
3. **需求要分层。** 有时核心需求只是看清楚、简单画一画，内置能力就够，不该触发任何技能；有时是学术图、经济学图这类特定场景，才值得上专用技能。academic-tikz 的 description 里把「快速草图」明确列为不适用，就是为了守住这条线。
4. **合并是路由设计。** 新的 SKILL.md 作为唯一入口，先判断任务类型（架构图、学科示意、数据图、动画、改图等），再路由到对应资产，而不是把三套文档拼在一起。

## 我的取舍与判断

**采纳**

- 合并为一个入口，同时不丢任何资产。目标是消除抢触发，不是做减法。
- 同名但内容不同的文件改名保留，内容完全相同的只留一份。去重只按「是否完全相同」这个客观标准。
- 上游 README 原样保留，并逐项标注来源，保证可追溯，也是对原作者的署名。
- 以本地 LaTeX 编译为底层，换取论文级的绘图质量。

**没采纳**

- 继续用 Python 画学术图：实测效果不理想。
- 三个技能并存：选择成本和迷失感会持续存在。
- 把统计数据绘图并进来：它仍由 python-data-figures 负责，README 里已明确分工。

**代价**

本地编译带来了安装门槛（需要 LaTeX 引擎和 poppler），这本身也是一种摩擦，与「降低摩擦」的初衷有张力。目前用环境自检脚本缓解，但还没有验证新用户能否顺利装好。
