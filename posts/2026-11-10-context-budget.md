## 一句话结论

上下文是一种预算，不是容器。Skills 的描述、模型的思考过程、工具返回的内容都在抢同一份预算；治理的方向应该是「谁该占用、占多少」，而不是把窗口越开越大。

## 背景：两件事撞到了一起

这两天有两件事让我把之前关于 skills 治理的想法串起来了。

一是 Claude Code 和 Codex 都开始管 skills 的**描述预算**。Agent Skills 的渐进式加载本来是为了省上下文：启动时每个技能只加载名称和描述（约 100 token），正文按需加载。但技能一多，光是这张清单就开始挤占窗口，于是两家客户端都加了限制机制——清单按上下文窗口比例截断，超出预算时描述被裁剪，甚至整个技能从清单里被省略。

二是我在 Artificial Analysis 的榜单上看到一个反直觉的现象：Fable 5.2 的 max 档位在 Intelligence Index 上整体分数最高（65），但在单独的 FrontierCode 2.0 编码测试里，High 得分 49.1%、Max 只有 48.8%。更高的思考档位没有带来更好的结果。

两件事看起来一个讲技能、一个讲模型，其实都在说同一件事：上下文里能放的东西是有额度的，而大家以前默认它无限。

## 先补一点背景：上下文治理是怎么变成问题的

早期用大模型，上下文更像"容器"：把资料贴进去，模型读完回答，装不下就分段。但 agent 起来之后，同一个窗口里同时挤进了四类东西——系统提示、工具与技能清单、对话历史、模型自己的推理链。它们不是排队进场，而是**每一轮都一起付费**。

于是业界慢慢形成了三层治理手段：

1. **入口层：渐进式披露（progressive disclosure）。** Agent Skills 的做法是启动时只加载每个技能的名称和描述，正文和 references 按需加载。这解决的是"东西还没用就先占着位置"。
2. **清单层：预算与裁剪。** 当技能多到描述清单本身成为负担，客户端开始给清单设额度、截断超长描述、把手动技能移出自动清单。这解决的是"光是目录就把目录占满了"。
3. **推理层：思考档位（reasoning effort）。** 模型在回答前生成多长的推理链，也可以调。链越长通常越强，但它自己写的中间 token 同样占上下文，还挤掉了留给任务材料的空间。

这三层共同指向一件事：**上下文不是免费的空间，而是每轮都要重新结算的预算**。我上一篇讲 skills 治理时说的是"注意力被摩擦耗尽"，那是从用户侧看；这一篇是从模型侧看，两边其实是同一个约束。

## 讨论中的关键点

1. **Skills 的「免费」是有额度的。** 每个技能约 100 token 的元数据，在 10 个技能时无关痛痒，在 100 个技能时就是一笔固定开销，而且每一轮对话都要重新付。Codex 会把初始 skills 清单限制在上下文窗口的约 2%（窗口未知时约 8000 字符），Claude Code 也有对应的清单预算参数。
2. **被裁剪的不是文字，是触发能力。** 技能靠 description 里的触发词被选中。清单一旦被截断或压缩，最容易被切掉的就是句尾的「Use when...」。结果不是"技能失效"，而是"技能还在，但再也不会被想起来"——这也是那篇分析里建议把触发词前置、把手动技能从清单里移除的原因。
3. **思考也占上下文。** Fable 5.2 在 AA 的完整 Index 上，输出 token 从 Low 档的 3490 万涨到 Max 档的 2.75 亿，平均每任务耗时从 6.5 分钟涨到 46.4 分钟。推理链越长，中间产生的 token 越多，留给任务材料、工具结果和指令的空间就越少。
4. **这正好解释了我之前的判断。** 我在 [skill-router-v3](https://github.com/Eastr5/skill-router-v3) 的重写里写过：模型已经被上下文充斥，还在抢用户的注意力，没有余量自己治理 skills。现在客户端的限制机制是同一个问题的另一面——不是模型不愿治理，是治理动作本身也要花上下文。

## 我的取舍与判断

**采纳**

- 把「上下文预算」当成产品的一等概念来设计：技能清单、推理长度、工具返回量应该共享一套可见的额度，而不是各自默认无限。
- 描述触发词前置、手动技能从清单移除、把长文档放进 `references/` 按需加载——这些是低成本高收益的做法，和我合并 academic-tikz 时「同一场景只留一个入口」是同一条逻辑。
- 评测要按难度分层。[skill-router-v3 的评测集](https://github.com/Eastr5/skill-router-v3/tree/main/evals)里我加了注册表膨胀实验（往 prompt 里注入几十个干扰能力），测的正是"上下文变挤之后路由还准不准"——现在看这个实验做对了。

**没采纳**

- 「窗口不够就开更大」。窗口变大只是把预算上限抬高，不解决谁该占用。而且长上下文本身有注意力稀释的问题，这点在 AA 的数据里能看到苗头，但我没有严格证据，不下结论。
- 「思考档位越高越好」。Max 在综合榜上 65 分确实最高，但成本约为 High 的 2.9 倍、耗时 2.6 倍，且在 FrontierCode 2.0 上反而略低。选档位应该按任务类型，而不是按"能不能开到最大"。

**关于「上下文溢出导致 max 变弱」这个猜想**

我的直觉是：推理链挤占了任务材料的空间，尤其在需要读大量代码或文档的 agentic 任务里，越想越偏。但这目前**只是一个猜想**——AA 的数据只能证明"更高档位不总是更强"，不能证明原因是上下文溢出，也可能是评分噪声、任务分布或采样差异。我在 skill-router-v3 的评测里已经吃过一次亏：单次跑分波动和实验效应同量级，所以这次不把猜想写成结论。
